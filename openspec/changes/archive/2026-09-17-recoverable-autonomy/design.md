## Context

验收报告的错误分为验证配置错误、源实现错误、缺失的修订入口和开销策略。现有空 writes 是未知范围并串行化，不能误称为只读。Native specs 继续约束验收。

## Decisions

1. run.revise 采用显式 before/after 预览、reason 与 plan_hash CAS，只替换待完成任务/阶段/里程碑检查。已完成任务、范围、source_ids、DAG、Git HEAD 和原生 Markdown 不修改。修订是运行账本中的有效覆盖，原 TOML 是规划基线；变更历史与原因进入 state.get 和审核证据，新 run 不继承覆盖。
2. 应用要求所有工作已处理或停止并撤销、集成 Git 状态已对齐、无未恢复意图、来源哈希一致。已通过任务保留；仅修订的任务建立新重试 epoch。旧失败与检查日志不删除。首次修订同事务设置账本 user_version=3，阻止旧版 v2 写入器丢失覆盖/历史；新服务兼容 v2/v3 控制和读取。幂等重放不会再次应用或启动工作。仅被本次检查修订替代的 host-verification 修复可清除；语义修复保持独立。随后 prepare(run_id) 继续，时间预算不自动延长。
3. 预检读取真实平台、工具位置、cwd、文件与声明写集。未生成的测试明确 deferred；不把预检冒充已通过测试。Node --test 目录输入是版本相关的可移植性风险，实际 MODULE_NOT_FOUND 才判为已证实的配置错误。规划候选被拒绝时记为失败，下一次准备新规划包携带诊断。
4. 细粒度原生任务可用同一执行任务的多个 source_ids 覆盖，合并相关实现与测试，仍验证全部原生顺序与验收。纯验证通常附着实现；确有独立需求时保留。不保证模型一定生成最少任务。
5. work.claim-batch 一次校验全部令牌、身份、fresh context 与全局会话约束后一次保存，失败零部分认领。
6. run.cleanup 默认预览，apply 使用计划哈希；覆盖失败、撤销、被替代的干净自有工作树。保留活跃/脏/锁定/未知/共享目录、集成分支与证据；可选仅删除已合入 accepted_head 且无 checkout 的自有分支，使用 SHA CAS。旧 cleanup CLI 保持立即清理且保留分支的行为。

## Validation

复现晚期错误检查，先接受一个任务再失败、修订、同 run 继续到交付；验证历史/提交/检查点保留。覆盖过期预览、活跃认领、旧修复失效、重复请求、批量原子性、错误规划重新派发、真实 Node 24 目录行为和 Git 清理安全性。完整回归及发布包测试；本轮不把 mock 运行时间当作真实 LLM 性能提升证据。
